**Q2 机制**

- 无参 `destroy()` 必带 `UND_ERR_ABORTED`，除非 `endEmitted` 为真（`readable.js:49-59`）。注意「已收完但没人读」的流 `endEmitted` 仍为假，照样带错（Q9B）。
- emit 是异步的，不是同步：`_destroy` 在无人读时走 `setImmediate(callback)`，随后 `process.nextTick(emitErrorCloseNT)`。所以「先 destroy 后挂监听器」也来得及（变体 (ii) 实测绿）。
- 已完整消费的流再 `destroy()` 无事，只发 `close`。证据：修复前构建上「正向」真网络用例（读完后 `res.destroy()`）通过。
- v26.13.0 与 v26.12.1 在这一点上无差异。
- 证据：`02-webclip-region-and-undici-readable.txt`、`08-node-internals-diff-and-destroy.txt`、`09-readable-fns.txt`。

**Q3 修复是否「对」**

- (a) 三处 `res.destroy()` 逐路径：
  - 重定向（:679）与 CT 白名单外（:704）：流从未被消费，无人会被「抢走」错误，noop 只是接住必发的 `UND_ERR_ABORTED`。
  - `finally` 正常读完：流已 end，`destroy()` 不带错，noop 不触发。
  - `finally` 的 too_large：迭代器 `return()` 自行销毁流，那个错误由迭代器自带的监听器接住，循环原样抛出 `too_large`。`finally` 里的 `destroy()` 落在已销毁的流上，是空操作。
  - `finally` 的中途断流或总预算撕断：迭代器先拒绝，已转成 `fetch_failed`，之后才进 `finally`。
  - 结论：noop 只在「没有消费方」或「消费方已收场」时挂上，不会造成静默挂起或截断当成功。
- (b) 没有窗口。`await` 的续体到 `for await` 首次 `next()` 在同一轮微任务里，`next()` 同步挂上 `readable` 与 `eos` 监听。即使 socket 错误与响应头同 tick 到达，undici 用 `queueMicrotask` 延后销毁，emit 还要再过一个 `setImmediate`。
- (c) `once` 够用。Node 保证每条流至多 emit 一次 `error`：`destroy()` 见已销毁即返回，`emitErrorNT` 有 `kErrorEmitted` 守卫，`onDestroy` 只回调一次。实测见 Q9。
- (d) `agent.close()` 时序无问题：`kAbort()` 在 `destroy()` 内同步执行，之后才 `close()`；每跳独立 Agent。我没有实测连接计数，这一点是读源码的推断。
- 证据：`02-*`、`05-undici-request-and-api-request.txt`、`09-readable-fns.txt`。

**Q9 二次 emit 探针**

- 设计：每个场景一个独立子进程，不装 `uncaughtException` 处理器。客户端 destroy 之后服务端在 0、1、3、10、30、80ms 关闭或 RST socket，另有 chunked 提前关闭与续写。先 destroy 后出错和先出错后 destroy 两种次序都落到了。
- 规模：两套 node 共 296 次裸跑，另有 56 次 capture 模式（装处理器记录「本应致命」的事件）。
- 二次 emit：0 次。带修复的 A 类与 D 类（含双重 destroy）存活样本里，每条流恰好 1 次 `error` emit，由 noop 接住。
- 「头到后立刻 socket 错误、无消费者」：带修复的代码也死。capture 模式下看到 `SocketError/UND_ERR_SOCKET` 或 `ECONNRESET` 在 0 个监听器时 emit。这是 M-1 的实测依据。
- 局限：服务端 0ms 即杀时请求常在拿到响应头之前就被拒（记为 rejected），这类样本没有进入 destroy 路径。
- 证据：`50-plan_big.txt` 的 Q9 行、`52-*`。
