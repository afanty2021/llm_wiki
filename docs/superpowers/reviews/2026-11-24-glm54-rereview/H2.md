#### Important

**I1. 自适应 idle_timeout 默认 60s + --progress 垫片覆盖面窄，静默但活跃的命令会被提前杀死（可用性回退）**
- 位置：tools/environments/base.py:541-556（读取配置与 60s 默认）、:584-600（idle 判定与 124 退出）；tools/terminal_tool.py:1181-1215（`_preprocess_command_for_adaptive_timeout`）；hermes_cli/config_defaults.py:302-309。
- 错在哪：垫片只在 `command.startswith('git clone')`（大小写敏感）时插入 `--progress`。检测正则（IGNORECASE、`\bgit\s+clone\b`）能识别 `cd x && git clone …`、`git -C d clone …`、`GIT … CLONE` 等形态，但改写分支接不住它们——这些命令没有进度输出，静默 60s 即被 idle 判定杀掉；而 fork 之前它们能活到硬超时（默认 180s）。同理 `python train.py`、大型构建等「合法静默 >60s」的命令全部提前死亡。另外 `gh repo fork/clone` 分支注入的 `GIT_PROGRESS=1` **不是 git 认识的环境变量**（读码推断；gh 自身行为离线无法核实）——该分支很可能完全无效，`gh repo clone` 大库依旧 60s 死。base.py 注释「silent long-runners hang forever otherwise」不成立：fork 前有硬超时兜底。
- 为何要紧：这是生产网关的 agent 终端主路径。教师服务场景里模型跑慢克隆/长脚本被 60s 掐断，任务失败且比 fork 前更早；网关级 activity 心跳（touch_activity_if_due）反而掩盖了问题（网关不杀，base.py 自己杀）。
- 怎么修：① 默认值提到 ≥300s（或与 terminal.timeout 同阶），0/negative 关闭语义保留；② 垫片改为对检测命中的任意形态插入（用正则在 `\bgit\s+clone\b` 命中点插入而非 startswith），或干脆以 `GIT_PROGRESS` 类手段不可靠为由只保留真 `git clone --progress` 并在工具 schema 描述里告知模型 idle_timeout 的存在；③ 验证 gh 进度通道真实机制后再保留该分支。

**I2. scripts/clear_zai_cache.py 以非原子、无锁写直改 live 凭据库 auth.json**
- 位置：scripts/clear_zai_cache.py:25-26（读）、:59-60（`open(auth_file, "w")` + `json.dump`）。
- 错在哪：auth.json 是网关的凭据存储（含 OAuth refresh token、credential pool）。仓内正规写入走 `_auth_store_lock()`（hermes_cli/auth.py:855-870 `_provider_state_transaction`，双锁 + 重读）与原子落盘；本脚本绕开锁、以截断方式原地重写。网关/CLI 并发写时是 last-writer-wins 的丢更新（最坏丢掉刚轮换的 refresh token）；进程中断在 dump 中途则留下截断 JSON——下次启动凭据解析失败。另外 `Path.home()/".hermes"` 硬编码，忽略 HERMES_HOME/profile home（multiplex 下清错文件还报「没有发现需要清理的缓存」）；也只清 `providers.zai`，全局 root auth.json 兜底源（auth.py:820-830 `_load_provider_state_with_source`）未覆盖。
- 为何要紧：这脚本正是故障应急工具，最可能在网关还活着时被手跑；对凭据完整性无保护。
- 怎么修：改为复用 `hermes_cli.auth` 的锁 + 原子写（tempfile + os.replace）；路径改走 `_auth_file_path()` / `get_hermes_home()`；或干脆提供 `hermes` CLI 子命令替代独立脚本。
